## 第 0 章 先认识这个项目（不用懂代码）

这个系统干两件事：

**第一件：知识库问答。** 你把一堆官方文件（公文条例、管理办法之类）上传进去，然后问它"医疗器械经营许可证有效期多久？"，它会翻资料、回答，并且告诉你答案来自哪份文件的第几段。资料里没有的，它会直接说"资料不足"，**不会瞎编**。

**第二件：公文工作流。** 你说"起草一份关于开展医疗器械自查的通知"，它会：
1. 判断你想干嘛（只是提问？还是要写文件？还是要统计？）
2. 去知识库翻相关材料
3. 按公文格式写一份草稿
4. 用 8 条检查规则给草稿"批改打分"
5. **停下来等你人工确认**（重要文件不能机器自己说了算）
6. 你点通过后，导出成文件

这两件事都靠"人工智能"，但它不是万能的，所以我们给它加了大量"安全绳"。这份文档的核心，就是让你看懂这些"安全绳"为什么存在、怎么起作用。

## 第 1 章 六个前置知识（非常关键，看懂这六个，后面的都好办）

### 1.1 HTTP 请求和响应：浏览器和后端怎么"说话"

**生活比喻——点外卖。** 你在外卖 App 上点了一份饭：你的手机把"我要一份牛肉面，不要辣"发给店家；店家回复"收到，订单号 6"。网页和服务器也是这么说话的：

- 你的**手机/浏览器** = 顾客
- **后端服务器** = 店家
- 你说的话 = **请求（Request）**
- 店家的回复 = **响应（Response）**

一次"说话"包含固定的几样东西：

| 部分 | 是什么 | 外卖里的对应 |
| --- | --- | --- |
| 方法 | GET = 只是"看/问"；POST = "提交一个动作" | GET 念菜单，POST 下单 |
| 地址（URL） | 你要找哪个功能 | 店家的哪条柜台 |
| 请求头 | 附带信息，比如"我的身份凭证" | 出示会员卡 |
| 请求体 | 真正要传的数据 | 订单内容 |
| 状态码 | 后端告诉你结果 | 200=成功，401=你还没登录，409=现在不行（状态不对），500=店家出错了 |
| 响应体 | 后端返回的数据 | 订单号和小票 |

真实例子（这个系统里"触发工作流"时前端干的事）：

```
POST /api/workflow/tasks                ← 方法 + 地址
Authorization: Bearer abc123...         ← 请求头：我是登录用户 admin
{ "question": "起草一份自查通知" }        ← 请求体：要办的事

← 响应：200
{ "code": 200, "data": { "id": 6, "status": "RUNNING" } }   ← 响应体：任务号 6，正在跑
```

> **记住这个就够了**：网页和后端靠"一问一答"通信。问叫请求，答叫响应，答必带状态码（成功还是失败，为什么失败）。

### 1.2 JSON：数据的"统一包装"

同一个数据要在各种语言之间传来传去——前端用 JavaScript，后端用 Java。它们怎么互相看懂？用一种叫 **JSON** 的统一格式：

```json
{ "question": "起草通知", "kbIds": [5, 6] }
```

像读英语一样读它就行：

- `{ }` 大括号 = 一个"包裹"
- `"名字": 值` = 包裹里的一个字段，冒号前面是标签，后面是内容
- `[ ]` 方括号 = 一个列表
- 所以这行意思是：**一个包裹，里面 question 字段是"起草通知"，kbIds 字段是一个列表，含 5 和 6**

在 Java 那边，这件事被自动完成了：后端有个类长这样：

```java
public record WorkflowCreateRequest(String question, List<Long> kbIds) {}
```

Spring 框架看到 JSON 包裹，自动把值塞进这个对象。你不需要手写解析代码——**这就是为什么后端看起来"没写什么却能用"**。

> **记住这个就够了**：JSON 就是一张"标签: 内容"的清单，前后端和数据库之间传数据全靠它。

### 1.3 数据库和表：数据住在带编号的 Excel 里

**生活比喻。** 数据库像一个 Excel 文件，里面有很多 sheet 页，每页是一张**表**。

- 一行 = 一条记录（比如"任务 #6"）
- 一列 = 一个字段（比如"问题""状态""创建时间"）
- **主键（id）** = 每行唯一的编号，像学号。行可以重名，学号不能重复。

这个项目有四张主要表：

| 表名 | 存什么 | 比喻 |
| --- | --- | --- |
| users | 用户账号 | 员工花名册 |
| knowledge_base | 知识库（资料的"文件夹"） | 档案室的柜子 |
| rag_document | 上传的文档、处理状态、分块数 | 柜子里的每一份文件 |
| workflow_task | 工作流任务的全部信息 | 办事大厅的受理单台账 |

操作数据只需记住三个单词（SQL 语言）：

```sql
SELECT * FROM workflow_task;                    -- 查（翻台账）
INSERT INTO workflow_task (...) VALUES (...);   -- 加（登记新单子）
UPDATE workflow_task SET status='CONFIRMED' ...  -- 改（在单子上盖章）
```

> **记住这个就够了**：数据存在表里，一行一条记录，id 是唯一编号，增删改查用 SQL。

### 1.4 线程：服务器里的"服务员"和"厨师"

这是整个项目**最重要的前置知识**，请慢慢看。

**比喻：餐厅。** 一家餐厅里：

- **服务员**（线程）负责接待客人。一位服务员同一时间只能服务一桌。
- 客人点了一道**要炖 60 分钟的菜**。如果服务员站着等这锅菜炖完，门口排队的客人全部饿着——这显然不行。
- 所以有**后厨**（线程池）：领班把"炖菜"这张单子丢进后厨，后厨里有一队**厨师**（池子里的线程）自己认领去做；服务员立刻回去接待下一桌，等菜好了再端过去。

对应到这个项目：

| 餐厅角色 | 项目里的东西 |
| --- | --- |
| 服务员 | Tomcat 的**请求线程**：每个 HTTP 请求分配一个 |
| 后厨 | **线程池** `workflowExecutor`（池里固定有 2~4 个线程干活） |
| 炖 60 分钟的菜 | 工作流任务：调用大模型生成公文，要 20~90 秒 |
| 厨师做菜 | 异步线程里执行 DocWorkflow 图 |
| 客人反复看取餐屏 | 前端每 2 秒**轮询**一次"好了没" |

为什么要这么设计？想象如果不用后厨：用户点"触发工作流"，服务员（请求线程）站在那儿等 60 秒，这 60 秒里浏览器会以为服务器死了（HTTP 一般 30 秒就超时断开）。所以**长任务必须扔到后台，接口立刻返回"收到，任务号 6"**。

**ThreadLocal（工牌）——一个必须知道的坑。** 服务员胸前挂着一块**工牌**，上面写着"我是谁、我有什么权限"。这块工牌就是 `ThreadLocal`：**它只属于挂它的那个人（线程）**。

问题来了：领班（请求线程）把做菜任务交给厨师（异步线程）时，**厨师没有服务员的工牌**。于是厨师拿着单子去仓库领高级食材，仓管说"你没工牌，不给"——这就是本项目真实踩过的坑：登录信息在异步线程里丢了，权限校验直接失败。

解决办法不是给厨师发工牌，而是**服务员在交单子之前，自己先去仓库把料领好**。代码里就是：创建任务时，在**请求线程**里把所有知识库的权限检查一遍，之后异步线程只管用检查过的结果。

> **记住这个就够了**：请求线程 = 服务员，超时长的活儿扔进线程池 = 后厨；ThreadLocal 工牌不跨线程，所以"要身份信息的检查必须在前台做完"。

### 1.5 向量（embedding）：把文字变成"坐标"

**比喻。** 假设给每段文字打三个分：像不像政策、像不像医疗、像不像财务。

```
"医疗器械经营许可证有效期五年"  →  (政策 8 分, 医疗 10 分, 财务 1 分)
"二类医疗器械要备案"            →  (政策 7 分, 医疗 9 分, 财务 1 分)
"本季度营业利润下滑"            →  (政策 1 分, 医疗 1 分, 财务 9 分)
```

你会发现：**意思相近的句子，分数也很接近**。

真实的 AI 模型（这个项目用的是 bge-m3）会自动找出 **1024 个**这样的维度，给每段文字打 1024 个分，这串分数就叫**向量**。于是"找相关内容"就变成了"**在 1024 维空间里找坐标最近的卡片**"——这就叫**向量检索**。它的厉害之处：你问"许可证有效期多久"，它也能找到原文写"经营许可证有效期为5年"的段落，哪怕字面不完全一样。

> **记住这个就够了**：向量 = 文字的"语义坐标"，意思越近坐标越近；向量检索就是找最近的坐标。

### 1.6 大模型与 RAG：开卷考试的实习生

**大模型（LLM）** 是一个读了很多书、很会说话的实习生。但它有两个毛病：

1. **没看过你们公司的内部资料**；
2. **不知道的时候也会一本正经地编**（行话叫"幻觉"）。

**RAG** 就是为了治这两个毛病的方法，全称"检索增强生成"，翻译成人话就是**开卷考试**：

- 你问问题，系统先去资料柜（知识库）翻出最相关的几段"书页"；
- 把这几页拍给实习生看，并说：**"只根据这几页回答，每句话注明出自第几页 [n]，这几页没写的就说资料不足。"**
- 实习生的答案就有了依据，你还能顺着 [n] 去核对原文。

这个"翻资料 → 给实习生看 → 要求标注出处"的完整流程，就是本项目的第一件大事（第 3 章细讲）。

> **记住这个就够了**：RAG = 先翻资料再回答，答案带出处；资料没有就拒答，不靠模型瞎编。

### 本章小结（背这三句）

1. 前后端靠 **HTTP 一问一答**说话，数据用 **JSON** 包着传。
2. 数据住在**数据库的表**里，行是记录，id 是唯一编号。
3. 长任务要丢给**线程池**后台做；**ThreadLocal 身份信息只属于当前线程**；**向量**让"找相近内容"成为可能；**RAG** 是给大模型开卷考试。

## 第 2 章 一个请求的一生（把整个系统串起来）

这一章不出现代码，只用一家"AI 办事餐厅"的比喻，让你先对整个系统有画面感。

### 2.1 六种"角色"

| 角色 | 在系统里是谁 | 干什么 |
| --- | --- | --- |
| 点餐屏 | 前端页面（Vue） | 用户点来点去的地方 |
| 服务员 | Controller（控制器） | 接待请求，检查单子格式对不对 |
| 领班 | Service（服务层） | 安排流程，决定谁先干、谁后干 |
| 后厨 | 线程池 + 工作流图 | 真正干活：翻资料、调 AI、检查格式 |
| 台账 | 数据库 | 每一张单子的状态和结果都记在这 |
| 档案室 | 知识库（pgvector） | 存着所有资料卡片，等着被翻 |

名字里的英文是通用的行业叫法：**Controller 管接客，Service 管流程**，这是几乎所有 Java 后端项目的固定分工。

### 2.2 「触发工作流」时，到底发生了什么

```
【第 1 分钟 — 前台】
你在页面输入"起草一份自查通知"，点击按钮
   ↓ POST /api/workflow/tasks（带着你的登录工牌）
服务员（Controller）把单子交给领班（Service）
   ↓
领班干三件事：
  ① 查工牌：你有权限用这些知识库吗？（没权限 → 403 打回）
  ② 登记：在台账（数据库）insert 一条新记录，状态写"RUNNING 执行中"，拿到单号 #6
  ③ 把单子丢进后厨（线程池），立刻转头对你说："收到，#6 正在做"
   ↓
浏览器拿到 #6，页面开始每 2 秒问一次："#6 好了没？"

【第 2 分钟 — 后厨（你看不到，但它在忙）】
厨师（工作流图）按菜谱一步步来：
   第一步 分诊（意图识别）：是要"提问"还是要"写文件"？→ 判定：写文件（DRAFT）
   第二步 翻档案（检索）：去知识库找出最相关的几段资料
   第三步 写草稿（生成）：让 AI 按公文格式写一份通知
   第四步 批改（格式检查 Skill）：用 8 条规则打分
   全部做完 → 在台账上把 #6 的状态改成"PENDING_CONFIRM 待你确认"

【第 3 分钟 — 又回到前台】
你的页面第 N 次问"好了没"，这次回答："待确认"
   ↓ 页面显示草稿 + 8 条批改结果 + 引用了哪几段资料
你核对后点【通过】 → 台账状态改成"CONFIRMED 已确认"
   ↓ 点【导出】 → 下载一个 .md 文件，台账状态改成"EXPORTED 已导出"
```

### 2.3 为什么中间非要"停下来等你"？

因为这是**公文**。公文发出去代表机关意志，写错一个文种（"请示"写成"报告"）都是事故。所以设计上故意留了一个**人工确认**环节：机器只是草稿和检查员，**签字盖章的人必须是你**。

这个"任务在什么阶段、下一步能做啥"的规则，叫**状态机**（第 4 章会讲），本质就是快递物流那种轨迹：已下单 → 运输中 → 待签收 → 已签收。

### 2.4 整章一句话

> 你点按钮 → 服务员接单 → 领班登记并丢进后厨 → 后厨按流程干完把结果记进台账 → 你确认 → 导出。整个系统的所有代码，都是在保证这条流水线的**每一步不出错、出错能看见、出格的动作被拦住**。

## 第 3 章 知识库问答是怎么工作的（RAG 详解）

还记得开卷考试的比喻吗？真实系统里，它拆成了 5 个步骤。我们一个一个来。

### 3.1 第一步：资料入库——把书切成卡片

你上传一份 3 万字的 PDF，系统不会把整本书直接丢给 AI（太大了，AI 记不住也找不准）。它做三件事：

1. **切块**：把文档切成一段一段的小块（这个项目存成了"分块"，每块几十到几百字）；
2. **量坐标**：用 bge-m3 模型给每块算一个 1024 维向量（1.5 节讲的"语义坐标"）；
3. **存好**：把"正文 + 坐标 + 出自哪个文件第几段"一起存进 **pgvector**（一个专门存向量的数据库插件）。

> 你去页面上传文档后看到状态从"处理中"变成"就绪"，背后就是这三步在跑。等它就是等"卡片都贴好坐标上了架"。

### 3.2 第二步：检索——两位图书管理员同时帮你找

你问"医疗器械经营许可证有效期多久？"，系统派**两位管理员**同时去找：

| 管理员 | 方法 | 擅长 |
| --- | --- | --- |
| 向量管理员 | 算出你问题的坐标，找坐标最近的卡片 | "意思相近"：你问"有效期"，他能找到写"期限为五年"的段落 |
| 关键词管理员 | 在正文里找字面相同的词（SQL 的 ILIKE 模糊匹配） | "字面一致"：文号、专有名词如"国药监市[2003]118号"，向量容易漏，他一把抓住 |

为什么要两个人？因为各有盲区。只靠向量，"许可证"和"注册证"可能混；只靠关键词，换个说法就全找不到。**两人一起找，互相补盲**——这叫**混合检索**。

项目里关键词管理员干活的那句 SQL，翻译成人话：

```sql
WHERE metadata->>'kb_id' IN (?, ?)     -- 只在我有权限的这两个知识库里找
  AND (text ILIKE ? OR text ILIKE ?)   -- 正文里含有任意一个关键词
LIMIT ?                                -- 每人最多带回来 N 张卡片
```

（`ILIKE` = 不区分大小写的"包含"。`?` 是占位符，真正的关键词值由程序填进去，防止有人往查询里塞坏东西——这叫防 SQL 注入。）

### 3.3 第三步：排名合并——两位老师的名次怎么合

问题来了：两位管理员各带回一个**排名列表**。向量管理员说"A 第一、B 第二"，关键词管理员说"B 第一、C 第二"。怎么合成一个总排名？

用 **RRF（倒数排名融合）**。规则非常简单：

> 每个人第 1 名得 1/(60+1) 分，第 2 名得 1/(60+2) 分……把两位管理员给的分**加起来**，总分高的排前面。

**为什么不是"名次相加除以 2"或者"加权平均"？** 因为两人打分的"尺子"不一样：向量管理员给的是 0~1 的相似度，关键词管理员压根没有分数、只有名次。尺子不同就不能直接相加分数——但**名次在两把尺子上是同样含义**，所以只拿名次来合成，最公平。（60 是论文里的经验参数，作用是让第 1 名和第 2 名的差距别太大，避免一家说了算。）

**最小示例（10 行 Java，可以单独跑起来理解）：**

```java
import java.util.*;

public class MiniRRF {
    public static void main(String[] args) {
        // 向量管理员给的排名（A 第一，B 第二）
        List<String> vecRank = List.of("A", "B");
        // 关键词管理员给的排名（B 第一，C 第二）
        List<String> kwRank = List.of("B", "C");

        Map<String, Double> score = new HashMap<>();
        for (int i = 0; i < vecRank.size(); i++)
            score.merge(vecRank.get(i), 1.0 / (60 + i + 1), Double::sum);
        for (int i = 0; i < kwRank.size(); i++)
            score.merge(kwRank.get(i), 1.0 / (60 + i + 1), Double::sum);

        score.entrySet().stream()
                .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
                .forEach(e -> System.out.println(e.getKey() + " 总分=" + e.getValue()));
    }
}
```

跑出来 B 排第一——因为**两位都把它排在了前面**。这就是 RRF 的核心思想：两边都认可的，才是真的好。

### 3.4 第四步：复赛——rerank 精排

初赛（上面的 RRF）只看了"名次"，没细看"内容命不命中"。所以再请一位严格的考官（**rerank 模型**，本项目用 bge-reranker）把前十名逐个和问题"面对面比对"重新打分，排出最终前几名。

它很准但很慢，所以只让少量候选进复赛——就像海选可以让很多人过，复试必须控制在十个人以内。

还有一个安全设计：如果考官请病假（rerank 服务挂了），系统**不会崩**，而是退回用初赛排名继续答题（这在代码里叫"降级"）。**功能可以有备胎，主流程不能停**，这是后端设计的重要习惯。

### 3.5 第五步：开卷考试——生成答案

现在系统手里有几段最相关的资料，把它们拍给 AI 看，并附上一张"工作说明"（**prompt**，就是给 AI 的指令便签）：

```
你是知识库问答助手。请根据下面的编号资料回答用户问题。
要求：
1. 只依据资料回答，在相关句子末尾用 [n] 标注引用的资料编号。
2. 资料不足时明确说明"知识库资料不足"，不要编造。
3. 使用中文回答。
用户问题：……
编号资料：
[1] (来源: 04_医疗器械监督管理条例.md)
……
[2] (来源: 21_医疗器械经营监督管理办法.md)
……
```

AI 就会输出类似："第三类医疗器械实行许可管理 [1]，许可证有效期为 5 年 [1]……"

你看到的 `[1]`、`[2]`，和页面下方"引用来源"列表一一对应——**这就是"引用标注文件名+段落"的实现原理**：编号体系从给 AI 看资料那一刻就建好了，而不是事后瞎标。

### 3.6 防瞎说三道保险（最重要的一节）

| 保险 | 做法 | 用大白话说 |
| --- | --- | --- |
| 保险 1：空手拒答 | 一段资料都没找到 → **根本不去问 AI**，直接返回"资料不足" | 书上没有，我不瞎说 |
| 保险 2：重试改问 | 找到资料但 AI 判断"不够回答问题" → 换个问法再翻一遍（最多 2 次） | 没翻到，换个书架找找 |
| 保险 3：拒答口吻 | 翻了两遍还不够 → 明确要求 AI："只说缺什么，禁止用你自己的知识回答" | 老师看着你呢，不许编 |

保险 1 为什么说"根本不去问 AI"很重要？因为**不调用 AI，就物理上不存在瞎编的可能**。这比在指令里求 AI"你别编啊"可靠一万倍——这也是这个系统拒答率能做到 100% 的根本原因。

代价也有：保险 2 每次重试都要再翻一遍资料，所以**问资料里没有的问题会慢一倍**（实测：有答案约 4 秒，没答案约 10 秒）。做产品就是在"准"和"快"之间做取舍。

### 本章小结

1. **入库** = 切块 + 算坐标 + 存起来；
2. **检索** = 向量（找意思近的）+ 关键词（找字面像的）双路，**RRF 只看名次合并**，再 rerank 复赛精排；
3. **生成** = 把资料拍给 AI + 要求标 [n] 出处；**三重保险防瞎说**，其中"没资料就不问 AI"是硬核保障。

## 第 4 章 公文工作流是怎么工作的

第 3 章讲的是"问答"，这一章讲"办事"。办事比问答复杂：要分情况、要按流程、要人签字。所以系统用了一个叫**工作流**的框架来组织。

### 4.1 先理解两个词：流程图和状态机

**流程图**（项目里叫"工作流/图"）：把一件复杂的事拆成几个**步骤**，步骤之间用**箭头**连起来，甚至可以分叉。

```
识别意图 → 翻资料 → 写草稿 → 格式批改 → 结束
```

**状态机**：规定一份任务"当前处于什么阶段、允许去哪里"。就像快递：

```
已下单 → 运输中 → 待签收 → 已签收
                     └→ 拒收 → 退回
```

每个阶段只能做规定的事：**没签收就不能评价**，**没确认就不能导出**。这种"非法动作直接拦住"的机制，对公文系统来说是刚需。

### 4.2 图里的 6 个"工位"

项目里的流程图有 6 个节点（node，就是一个工位）：

| 工位 | 干什么 | 类比 |
| --- | --- | --- |
| classify 分诊 | 判断你的话属于哪类：提问 / 写文件 / 统计 / 闲聊 | 医院分诊台 |
| retrieve 找资料 | 去知识库翻出相关段落 | 档案员取卷宗 |
| generate 写答案 | 让 AI 写草稿或回答问题 | 笔杆子写文件 |
| formatCheck 批改 | 用 8 条规则给草稿打分 | 语文老师批改作文 |
| stats 统计 | 查数据库：库里有多少文档、多少分块 | 管理员查台账 |
| chat 闲聊 | 调一个网络接口拿当前时间，陪你说句话 | 前台接电话 |

连接方式（这就是整个工作流的"地图"）：

```
开始 → 分诊 ┬→ 找资料 → 写答案 → 批改 → 结束     （想提问、想写文件，都走这条）
            ├→ 统计 → 结束                       （问"库里有多少文档"走这条）
            └→ 闲聊 → 结束                       （问候、"几点了"走这条）
```

注意"分诊后走哪条路"是**看情况决定的**，而且不是二选一，是四选一。这种"根据条件选通道"的连接，叫**条件分支（条件边）**，是这套框架最值钱的能力之一——不用写一堆 if-else 粘在一起，流程本身就是图。

### 4.3 分诊台（意图识别）是怎么工作的

分诊台没有真人，它让 AI 看一句话再回答一个 **JSON**：

```json
{ "intent": "DRAFT", "keywords": ["医疗器械", "经营许可", "自查"] }
```

意思是："这是要写文件（DRAFT），顺便帮我提取三个检索关键词"。

这里藏着一个新手最容易忽略的设计：**给 AI 的指令要极其明确**。项目里分诊的指令便签是这样写的（翻译版）：

> 判断用户意图，只输出 JSON：{"intent": "QA|DRAFT|STATS|CHAT", "keywords": [...]}
> QA 是查政策规定；DRAFT 是要求起草公文；STATS 是问文档统计；CHAT 是问候闲聊。

指令里把四类**定义清楚**、把输出**格式固定**，AI 的结果才稳定可用。

那 AI 万一不听话呢？两道保险：

1. 输出不是四类之一（比如它冒出个 WEATHER）→ 代码检查不通过，按最保守的 QA 处理；
2. AI 接口直接出错 → 也一样兜底按 QA 走，并在流程轨迹里记一笔"走了兜底"。

**为什么要兜底而不是报错？** 因为分诊只是"路由信息"，走错通道顶多答得差点；但如果整个任务报错，用户就什么都没得到。**宁可降级，不要崩**——这是这个项目遍布各处的统一思路。

### 4.4 写答案工位（generate）：两种写法

分诊让写文件（DRAFT）和只是提问（QA），用的是**两张不同的指令便签**：

- 写文件：要求标题规范、主送机关、"一、（一）1."的层次、"（待补充）"占位、文末落款日期、引用标注 [n]——**六条格式要求**；
- 提问：只依据资料 + 标注 [n] + 资料不足就直说。

你会发现写文件那六条要求，和第 4.5 节批改的 8 条规则**几乎一一对应**。这是故意的：

- **指令便签** = 事前约束：尽量让 AI 一次写对；
- **批改规则** = 事后检查：AI 没写对，代码必须能发现。

事前靠 AI 自觉（概率性），事后靠代码检查（确定性）。**两道闸门**，缺一不可。

### 4.5 批改工位（formatCheck）：8 条检查规则

这是整个项目里最"人味"的部分：8 条规则全部来自《党政机关公文处理工作条例》，写成了一个叫 **Skill**（技能）的组件。它**不调用 AI**，纯粹用代码查，所以同一个草稿永远得到同一个分数。

| 编号 | 检查什么 | 不合格的严重程度 |
| --- | --- | --- |
| R1 | 标题里有法定文种（通知/报告/请示/函…共 15 种） | 硬伤 |
| R2 | 标题不超过 50 字、结尾不带标点 | 硬伤 |
| R3 | "请示"和"报告"不能混在同一个标题 | 硬伤 |
| R4 | 通知/请示/报告/函 要有主送机关（第二行以"："结尾） | 提醒 |
| R5 | 用了"（一）"就必须先有"一、"（层次不能跳级） | 提醒 |
| R6 | 文末要有成文日期 | 硬伤 |
| R7 | 请示类要有"妥否，请批示"这种结语 | 提醒 |
| R8 | 正文不能太短（≥50 字） | 硬伤 |

打分规则很直白：**满分 100，每个硬伤扣 20 分，每个提醒扣 8 分，最低 0 分**。有任何一个硬伤就判"不通过"。

**为什么批改不用 AI，而用死规则？** 三个理由：

1. **确定性**：同个草稿查两遍必须一个结果，规则天然满足；AI 做不到。
2. **说得清**：用户问"为什么 72 分？"规则能精确回答"R5、R6 两条没过"；AI 打分只能回答"我觉得……"。
3. **免费且飞快**：调 AI 要钱要秒级等待，规则是毫秒级、零成本。

反过来，规则也有短板：它查不了"这份通知写得得体不得体"。所以规则管**格式**，内容好不好靠人看——这就是为什么后面必须有人工确认。

> **真实小故事（面试可讲）**：测试时发现一个误报——草稿明明写了"一、自查对象和范围"，R5 却说"缺一、"。查了半天发现：公文正文每行行首有一个看不见的"全角空格"，而检查代码找的是"行首的一、"；这个空格挡在中间，就找不到了。修复办法是查之前先把全角空格换成普通空格。教训：**中文排版里藏着看不见的坑；规则检查必须用真实生成的草稿去测。** 修完之后，同一份任务从 72 分变成了 100 分。

### 4.6 人工确认：为什么机器不能自己盖章

图跑完之后，任务**不会自动完成**，而是停在"待确认"，把三样东西摆到你面前：

1. 草稿全文；
2. 8 条批改结果（分数 + 每条通过与否）；
3. 引用了哪些资料（文件名 + 第几段）。

你核对后有两个选择：

- **通过**（CONFIRM）→ 状态变"已确认"，接下来可以导出；
- **驳回**（REJECT）→ 状态变"已驳回"，可以原样重跑，也可以改要求后重新发起。

为什么要这样设计？批改没通过也照样让你确认——因为**过不过关的最终决定权必须是人**。机器只负责把问题摆出来：格式硬伤标红、提醒标黄，剩下你决定是重跑还是导出。系统的角色是"助理"，不是"决策者"。

### 4.7 两个工具：查台账和打电话

工作流里除了 AI，还有两个"**工具（tool）**"——就是两段普通代码，干活快且准：

**工具 1：查台账（KbStatsTool）。** 你问"知识库里有多少文档？"，它直接查数据库，一条 SQL 数出来"共 2 个库、22 份文档、260 个分块"。这种问题**根本不需要 AI**：数字问题让 AI 数，既慢又可能数错。

**工具 2：打电话问时间（HttpTimeTool）。** 你说"现在几点了？"，它真的发一次 HTTP 请求到服务自己的时间接口，拿回"2026年11月25日 10:13:20"。为什么要这么绕？这是为了演示"**工具调用**"这种能力——真实系统里工具可以是查天气、查快递、调支付接口，思路完全一样：**能确定的活就别麻烦 AI**。

两个工具都遵守同一个约定：干活成功返回"我成功了 + 数据"，失败返回"我失败了 + 原因"。工作流拿到结果后如实转述，**工具挂了任务也不中断**。

### 4.8 任务状态机：6 个状态

现在把第 4.1 节的快递比喻换成代码里的正式名字：

| 状态 | 含义 | 能做的动作 |
| --- | --- | --- |
| RUNNING | 后厨正在做 | 等 |
| PENDING_CONFIRM | 做完了，等你确认 | 确认通过 / 驳回 |
| CONFIRMED | 你确认了 | 导出 |
| REJECTED | 你驳回了 | 重跑 |
| EXPORTED | 已导出 | 可以再下载一次 |
| FAILED | 中途出错 | 重跑 |

几条重要的"门禁"：

- 没到"待确认"就想导出？系统回 **409（现在不行）**，不带你钻空子；
- 确认只能在"待确认"状态做——两个页面同时点确认也只会有一个成功（第 5 章讲原理）；
- **已导出**之后还能再下载（下载是"看"，多看几遍无妨）；但想再确认一次？不行，状态不对。

### 本章小结

1. 工作流 = **流程图**（6 个工位 + 条件分支）+ **状态机**（6 个状态管着"下一步能做什么"）；
2. **分诊**让 AI 输出 JSON，**两道兜底**（非法值按 QA、出错按 QA）保证流程不中断；
3. **写文件靠指令便签事前约束，批改靠 8 条规则事后检查**，两条闸门加人工签字，才是公文系统的正确姿势；
4. 数字类的活交给**工具**（查数据库、调接口），**能确定的事不麻烦 AI**。

## 第 5 章 数据是怎么存下来的（数据库视角）

### 5.1 任务台账长什么样

工作流每个任务都存在 `workflow_task` 这张表里。把它想象成办事大厅的受理单：

| 列名 | 存什么 | 举例 |
| --- | --- | --- |
| id | 单号（主键，自动递增） | 6 |
| question | 你的原话 | 根据……起草一份通知 |
| kb_ids | 用哪几个知识库（逗号隔开的编号） | 5,6 |
| status | 当前处于哪个状态 | PENDING_CONFIRM |
| intent | 分诊结果 | DRAFT |
| draft | 草稿全文 | 药品监督管理局关于……通知 |
| format_report | 8 条批改结果的 JSON | {...} |
| sources | 引用了哪些段落（JSON 列表） | [...] |
| steps | 每个工位的执行轨迹（JSON 列表） | [...] |
| confirm_comment | 你确认/驳回时写的备注 | 公文核对无误 |
| error_msg | 出错原因（成功时为 NULL） | 生成失败：超时 |
| created_by / created_at / updated_at | 谁创建、什么时候建、什么时候最后修改 | admin / 时间 |

> 为什么 draft、sources 这些东西都是"JSON 字符串"存一列，而不是拆成很多表？因为它们是**成品快照**——存下来那一瞬间的完整结果，以后读出来展示即可，不需要对里面每一段单独查询。等哪天需要"按段落搜索历史草稿"了，再拆表也不迟。

### 5.2 状态是怎么变的：一句带条件的 UPDATE

新手常见的写法是"先查状态、判断、再改"：

```java
// 做法 A：先查后改（有隐患，项目里没用）
String status = 查询当前状态(id);
if (status.equals("PENDING_CONFIRM")) {
    更新状态(id, "CONFIRMED");
}
```

隐患在哪儿？如果两个地方同时执行这段代码：都查到"待确认"、都判断通过、都去更新——就重复确认了。这叫**竞态**。

项目用的是做法 B，一句话 SQL 里**既检查又修改**：

```sql
UPDATE workflow_task
SET status = 'CONFIRMED'
WHERE id = 6 AND status = 'PENDING_CONFIRM';   -- 只有当前确实是待确认，才改得动
```

改完数一下"影响了几行"：1 行 = 改成功；0 行 = 状态不对，拒绝。这就像银行取号机：**号码不对，窗口不给你办**。数据库保证这种"检查 + 修改"要么一起成功、要么一起不成功，中间不会被别的请求插队。

### 5.3 一个新手必踩的坑：PG 数据库拿不到"刚生成的 id"

新增一条记录后，程序要马上知道它的 id（后续都要用）。正常写法是 `getKey()`，但在 PostgreSQL 下会报错。通俗解释：

- 驱动（Java 连数据库的中间件）在你插入后，会给你**寄回一整个信封**（整行数据）；
- 而 `getKey()` 只准备接**一张写着一个数字的纸条**；
- 信封塞进纸条口，直接卡住报错。

修复办法：提前声明"我只要 id 这一列"，信封里就只装 id：

```java
PreparedStatement ps = con.prepareStatement(
        "INSERT INTO workflow_task (...) VALUES (?, ?, ?)",
        new String[]{"id"});   // ← 关键：只要 id 列
```

这个坑在这个项目里踩了**两次**（第一次在知识库模块）。同一个错踩两次，才配叫"教训"。

### 5.4 老环境的兼容小动作

建表语句一般写在初始化脚本里（`init.sql`）。但 Docker 数据库有个特点：**数据卷已经存在时，初始化脚本不会重跑**。老电脑上数据库是旧版本，没有新表，一用就报错。

所以项目在代码里加了一道保险：程序启动时执行一句 `CREATE TABLE IF NOT EXISTS workflow_task (...)`——表不存在就建，存在就跳过。**初始化脚本 + 代码兜底**，谁缺谁补。

### 本章小结

1. 一张表存一个任务的全部信息，成品内容（草稿/引用/轨迹）直接存 JSON；
2. 状态迁移用**带条件的 UPDATE**，一句 SQL 同时完成检查和修改，避免并发重复操作；
3. **PG 拿主键必须指定只要 id 列**；老环境靠 `CREATE TABLE IF NOT EXISTS` 兜底。

## 第 6 章 页面是怎么显示的（前端视角）

前端用 **Vue**（一个网页开发框架）。这一章只看四个新手最该懂的细节。

### 6.1 轮询：反复看取餐屏

后端是"丢给后厨就返回"，前端怎么知道做完了？**每 2 秒问一次**：

```javascript
setTimeout(async () => {
  current.value = await api(`/api/workflow/tasks/${current.value.id}`)  // 问：好了没？
  schedulePolling()   // 问完再排下一次（上一轮结束才排下一轮）
}, 2000)
```

为什么不把"任务完成"直接推给你？能做但复杂（要长连接）；轮询实现简单、断线自动恢复，对当前规模够用。这是典型的**技术选型看规模**：一百个用户轮询没问题，十万个用户就得换方案。

小细节：用的是"问完再排下一次"而不是"每 2 秒定时问"——后者在服务器慢的时候会堆积一堆没回的请求，前者永远不会。

### 6.2 流程条上的颜色是哪来的

页面顶部那排小格子（意图识别→检索→生成→批改），颜色**不是前端猜的**，而是后端每个工位干完活都记了一笔轨迹：

```json
[{ "node": "classify", "status": "ok" },
 { "node": "retrieve", "status": "ok", "detail": "命中 5 段" },
 { "node": "generate", "status": "ok" },
 { "node": "formatCheck", "status": "ok", "detail": "score=100, passed=True" }]
```

前端拿到这个列表，给每个格子上色：成功绿、出错红、兜底黄、跳过灰。**前端只负责展示，不负责判断执行到哪了**——单一信息源，前后端不会吵"明明完成了他那边显示没完成"。

### 6.3 导出：把文件从后端搬到浏览器

导出和之前所有接口都不一样：别的接口返回 **JSON**，导出返回的是一个**文件**（Markdown）。所以前端不能用公共的请求封装（它默认拆 JSON），要单独写：

```javascript
const res = await fetch(导出地址, { headers: { Authorization: `Bearer ${token}` } })
const blob = await res.blob()        // 把文件内容接住
// 生成一个临时下载链接，模拟点击一下，浏览器就开始下载了
```

### 6.4 确认弹窗

弹窗只有两个按钮：通过 / 驳回，加一个可选备注。按钮显隐完全听状态机指挥：

- 状态是"待确认" → 显示【人工确认…】按钮；
- 状态是"已确认/已导出" → 显示【导出】按钮；
- 状态是"已驳回/失败" → 显示【重跑】按钮。

**页面不判断业务规则，只按状态显示**——规则都在后端，前端永远只是"状态机的镜子"。这是前后端分工的黄金法则。

### 本章小结

1. 轮询 = 每 2 秒问一次"好了没"，问完再排下一次；
2. 流程条颜色来自后端记录的 `steps` 轨迹，前端只管展示；
3. 导出返回文件而非 JSON，要单独处理；
4. **前端是状态机的镜子**，判断逻辑全部在后端。

## 第 7 章 自己把它跑起来（零代码体验）

这一章不写一行代码，只让你把这个系统亲眼看一遍。需要电脑上装好 Docker、JDK 17、Node.js（项目里原来就有）。

### 7.1 启动三件套

按照顺序，每步确认没报错再下一步：

```powershell
# ① 启动数据库（一个装了向量插件的 PostgreSQL 容器）
cd E:\Project-Study
docker compose up -d

# ② 启动后端（第一次要下依赖，会比较慢）
cd E:\Project-Study\backed
.\mvnw.cmd spring-boot:run

# ③ 另开一个窗口，启动前端
cd E:\Project-Study\front
npm run dev
```

最后打开浏览器访问 **http://localhost:5173**，用账号 `admin` / 密码 `admin123` 登录。

另外说明：知识库问答需要**向量模型**，本机通过 Ollama 提供（bge-m3）；如果问答时报"嵌入失败"，先检查 Ollama 是否在运行。

### 7.2 三条体验路线（建议按顺序）

**路线 1：知识库问答（/kb/chat）**
1. 问："医疗器械经营许可证的有效期是多久？" → 看答案里的 `[1]` 和下方引用列表；
2. 问："我们公司员工年假的审批流程是什么？" → 看它拒答（这句话资料里根本没有）；
3. 对比两次的响应速度——有答案的约 4 秒，拒答的约 10 秒（多花在两遍重试）。

**路线 2：公文工作流（/workflow）**
1. 输入"根据医疗器械监督管理条例，起草一份关于开展医疗器械经营合规自查的通知"，点击触发；
2. 盯页面：每 2 秒自动刷新，四个工位依次变绿；
3. 完成后看三块内容：公文草稿、8 条批改报告、引用来源；
4. 点【人工确认…】→ 填备注 → 【通过】→ 再点【导出】下载 .md 文件；
5. 继续玩：新任务点【驳回】→ 看状态变"已驳回"→ 点【重跑】→ 再确认；
6. 试试"统计一下知识库的文档入库情况"（走数据库工具）和"现在几点了"（走 HTTP 工具）。

**路线 3：看评测报告（不开浏览器）**

打开 `logs/eval_report.md`，里面是 15 道题（10 道知识库里有答案 + 5 道没有）的自动评测结果：

| 指标 | 结果 | 验收线 |
| --- | --- | --- |
| 有答案题命中率 | 10/10 = 100% | ≥70% |
| 无答案题拒答率 | 5/5 = 100% | ≥80% |
| 引用标注率 | 10/10 = 100% | 100% |

### 7.3 卡住了怎么办（新手常见问题表）

| 现象 | 最可能的原因 | 怎么办 |
| --- | --- | --- |
| 页面 404 / 打不开 | 前端没启动 | 回到第③步看终端有没有报错 |
| 登录提示密码错误 | 数据库没启动/没初始化管理员 | 先 `docker compose up -d`，重启后端 |
| 问答报"嵌入失败" | Ollama 没开 | 启动 Ollama，确认 bge-m3 已下载 |
| 文档一直是"处理中" | 向量模型还在跑 | 耐心等；大批文档十几分钟正常 |
| 工作流一直"执行中" | 大模型接口超时 | 看后端日志有没有报错；可点重跑 |
| 导不出文件 | 还没确认 | 先【人工确认】通过，再导出 |

### 本章小结

三条路线从上到下依次体验：**问答看引用和拒答 → 工作流看节点点亮和人工确认 → 评测报告看数字**。体验完再回头看前面的章节，会有"哦原来是这样"的感觉。

### 8.3 下一步学什么（建议顺序）

你现在看的是"一栋盖好的房子"。想真正学会盖房，推荐按这个顺序补：

1. **Java 基础**：类、接口、record、集合、异常（本项目代码大量用这几样）；
2. **Spring Boot**：`@RestController`/`@Service`/`@Component` 注解、依赖注入、`application.yaml` 配置；
3. **JDBC / JdbcTemplate**：手写 SQL 查改数据库；
4. **并发基础**：线程、线程池 `ThreadPoolExecutor`、ThreadLocal（对应第 1.4 节）；
5. **HTTP 深入**：状态码语义（401/403/409/500）、SSE 流式响应；
6. **LangChain4j 一通百通**：ChatModel、EmbeddingModel、EmbeddingStore 三个概念就够用；
7. **langgraph4j**：StateGraph → 节点 → 边 → 条件边 → compile/invoke（看完本项目 DocWorkflow 就是最好的例子）。

给自己定节奏：每周只吃透一个大项，**每个大项都回到这个项目里找到对应的使用处**——看得见"学了马上用在哪"，才不容易忘。

### 8.4 全文档一句话总结

> 这个系统就是给大模型配了五道保险：**翻资料（RAG）防没依据、双路检索防漏找、8 条规则防格式错、人工确认防机器乱说话、状态机防乱操作**。你以后写的每一个 AI 功能，都值得按这五道保险的思路检查一遍。
