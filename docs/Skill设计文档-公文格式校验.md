# Skill 设计文档：公文格式校验（OfficialDocFormatSkill）

> W4 实践任务 E7 交付物之一。实现代码：`backed/src/main/java/com/intern/backed/workflow/skill/OfficialDocFormatSkill.java`

## 1. 定位与目标

在公文工作流「意图识别 → 检索 → 生成 → **格式校验** → 人工确认 → 导出」中，格式校验是生成之后、人工确认之前的**确定性守门环节**：

- LLM 生成的公文草稿可能存在文种缺失、请示报告混用、缺落款日期等格式问题；
- 用规则引擎（而非再调一次模型）做校验，结果**确定、可复现、零成本、零延迟**；
- 校验报告随任务落库并展示在人工确认页，辅助确认人快速判断"通过 / 驳回"。

## 2. 规则依据

规则来源于知识库资料《党政机关公文处理工作条例》（中办发〔2012〕14号）：

| 规则 | 名称 | 级别 | 条例依据 | 判定逻辑 |
| --- | --- | --- | --- | --- |
| R1 | 法定文种 | ERROR | 第八条：公文种类 15 种 | 标题须包含 决议/决定/命令/公报/公告/通告/意见/通知/通报/报告/请示/批复/议案/函/纪要 之一 |
| R2 | 标题规范 | ERROR | 第九条（七）：标题准确简要 | 首行非空、≤50 字、末尾不用标点 |
| R3 | 请示报告分开 | ERROR | 第十五条（四）：不得在报告中夹带请示事项 | 标题不得同时含"请示"与"报告" |
| R4 | 主送机关 | WARN | 第九条（八）：主送机关 | 通知/请示/报告/函 的第二行应为顶格"×××："（≤60 字） |
| R5 | 层次序数 | WARN | 《格式》国家标准：一、→（一）→1.→（1） | 出现"（一）"级时必须先有"一、"级 |
| R6 | 成文日期 | ERROR | 第九条（十二）：署发文机关和成文日期 | 全文须匹配阿拉伯数字或汉字日期（如 2026年11月25日） |
| R7 | 请示结语 | WARN | 行文惯例：期复用语 | 请示类须含"妥否/当否/请批示/请批复/请审核" |
| R8 | 正文完整 | ERROR | 生成质量兜底 | 去掉标题后正文 ≥50 字，防生成截断 |

分级策略：**ERROR**（硬伤，任一不通过即 `passed=false`）与 **WARN**（瑕疵，扣分但不阻断）。
评分：`score = max(0, 100 - ERROR数×20 - WARN数×8)`。

## 3. 接口契约

```java
FormatReport check(String draft)      // 结构化报告
String checkAsJson(String draft)      // 落库用 JSON
Map<String,Object> checkAsMap(String) // 图状态用 Map
```

输出示例：

```json
{
  "passed": false,
  "score": 72,
  "items": [
    {"rule":"R1","name":"法定文种","severity":"ERROR","passed":true,"message":"标题包含法定文种"},
    {"rule":"R6","name":"成文日期","severity":"ERROR","passed":false,"message":"缺少成文日期（如\u201c2026年11月25日\u201d…）"}
  ]
}
```

## 4. 在工作流中的接入

- 节点：`DocWorkflow.formatCheck`（`generate → formatCheck → END`）。
- 仅 `intent=DRAFT` 执行校验；QA/STATS/CHAT 输出 `{"skipped":true,"passed":true}`。
- 报告存入 `workflow_task.format_report`，前端确认弹窗按 ERROR/WARN 分色展示。
- **校验不通过不会自动驳回**——最终决定权在人工确认环节（人机协同：机器给证据，人做决策）。

## 5. 设计取舍

| 决策 | 理由 | 放弃的替代方案 |
| --- | --- | --- |
| 纯规则引擎，不调模型 | 格式规范是确定性知识，规则可解释、可单测、零 token 成本 | 再调一次 LLM 打分（慢、贵、不稳定、难解释） |
| ERROR/WARN 两级而非一票否决 | 主送机关、结语属于可容忍瑕疵，交给人工权衡 | 全部 ERROR（误杀率高，人工确认形同虚设） |
| Skill 独立 @Component，不依赖图 | 可单独复用（如未来上传公文体检）、可单测 | 把规则写死在 formatCheck 节点里（不可复用） |
| 校验失败仍进 PENDING_CONFIRM | 培养要求"人工确认可回退"，机器不越权做终态决策 | 校验失败直接 FAILED（人失去修正机会） |

## 6. 已知边界与后续优化

- 只做**文本层**校验，不校验版式（字体、字号、红头、版记）——纯文本导出场景够用；若导出 docx 需扩展 GB/T 9704 版式规则。
- R4 主送机关判定基于"第二行以：结尾"的启发式，对公告/通告类已豁免；复杂抬头（多个主送机关分行）可能漏判。
- 优化方向①：把校验结果反馈给生成节点做一轮自动修复（formatCheck → regenerate 条件边）；②：规则配置化（yaml 定义规则表，热更新）。

## 7. 验证方式

- 单元可测：`check()` 为纯函数，输入草稿字符串即可断言 8 条规则的 passed。
- 集成验证：前端提交 DRAFT 任务（如"起草一份关于开展公文格式自查的通知"），确认页应展示 8 条规则明细与得分；导出文件中格式要素齐全。
