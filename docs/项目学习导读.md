## 3. W2 基线导读（一）：SSE 流式对话

### 3.1 关键文件

| 文件 | 看什么 |
|---|---|
| `chat/DeepseekStreamChat.java` | SSE 事件协议的全部服务端逻辑（172 行，值得逐行读） |
| `config/DeepSeekSteamAssaistent.java` | LangChain4j AiService 声明式接口：@SystemMessage(fromResource) + @V 模板变量 + @MemoryId |
| `config/MemoryConfig.java` | ChatMemoryProvider：每个 memoryId 一个 10 条消息窗口 |

| `resources/messagePrompt.md` | 系统提示词，{{style}} 由接口参数注入 |
| `front/src/views/ChatViews.vue` | 前端手动解析 SSE 帧（fetch + ReadableStream，不用 EventSource） |

### 3.2 事件协议（固定顺序）

| event | data | 时机 |
|---|---|---|
| `meta` | {messageId, conversationId} | 建流后立即发，前端由此拿到会话 ID |
| `token` | {delta} | 模型每产出一点文本就推一条 |
| `done` | {finishReason, firstTokenMs, usage} | 正常结束；finishReason=length 表示被截断 |
| `error` | {code, message, traceId} | 模型侧异常；code 分 MODEL_TIMEOUT / MODEL_RATE_LIMITED / MODEL_ERROR |

### 3.3 核心机制（面试重点）

1. **校验前置**：`@Valid` 失败直接走 GlobalExceptionHandler 返回 400 JSON，**不建立 SSE**。前端因此要区分"response.ok=false时读 JSON"和"OK 后读流"两条路径（ChatViews.vue 第 115-126 行）。
2. **并发状态守卫**：`AtomicBoolean finished` + `AtomicLong firstTokenMs`。模型回调线程和 Servlet 容器线程（onTimeout/onError/onCompletion）可能并发，`compareAndSet(-1, …)` 保证首字耗时只记一次，`compareAndSet(false, true)` 保证 emitter.complete() 只调一次。
3. **客户端断连不炸服务端**：每次 `emitter.send` 都 catch IOException/IllegalStateException，置 finished 后静默停止推送；模型回调里先查 `finished.get()` 直接 return。
4. **首字延迟双端测量**：后端 `System.nanoTime()` 差值记 firstTokenMs（模型耗时），前端 `performance.now()` 记浏览器视角耗时——两者对比可区分"模型慢"还是"网络/代理慢"。
5. **反缓冲**：响应头 `X-Accel-Buffering: no` + `Cache-Control: no-cache`，防 Nginx 等中间层攒包导致"整段一次性出现"。
6. **会话记忆键**：`memoryId = userId + ":" + conversationId`，MessageWindowChatMemory 只保留最近 10 条；换新会话=换 conversationId。
7. **前端为什么不用 EventSource**：EventSource 只支持 GET 且不能带请求体；这里用 `fetch POST + response.body.getReader()` 手动按空行分帧、按 `event:`/`data:` 前缀解析，还处理了 UTF-8 半个中文字符跨 chunk 的问题（`decoder.decode(value, {stream:true})`）。
8. **前端 XSS 双保险**：markdown-it `html:false` 禁原始 HTML + DOMPurify.sanitize 后再渲染。

### 3.4 面试问答

**Q：SSE 和 WebSocket 怎么选？**
A：SSE 是单向服务端推送、基于 HTTP、自动重连、天然过代理；对话场景"一问一答流式回"只需要下行推送，SSE 足够且更简单。WebSocket 是全双工，适合聊天室、协同编辑等需要双向实时的场景。

**Q：为什么用 POST 而不是标准 SSE 的 GET？**
A：问题文本可能很长（4000 字上限），放 URL 会超长且被日志记录；POST body 更合适。代价是不能用 EventSource，前端要手动解析流——本项目正是这么做的。

**Q：模型回调在哪个线程？为什么要原子变量？**
A：LangChain4j 流式回调在 HTTP 客户端的 IO 线程，与 Servlet 线程并发。finished/firstTokenMs 被多线程读写，AtomicBoolean/AtomicLong 的 CAS 保证"只记一次首字、只 complete 一次"，避免重复 complete 抛 IllegalStateException。

**Q：ChatMemory 会不会无限膨胀？**
A：单会话有 10 条窗口上限，但 memoryId→memory 的映射在内存里只增不减（默认 InMemoryChatMemoryStore），长期运行会积累。改进方向：持久化 Store + TTL 淘汰，或 Redis。这是可以主动讲的"我知道的局限"。

**Q：用户中途关页面，服务端怎么办？**
A：send 抛 IOException → finished=true → 后续 token 直接丢弃；emitter.onError/onCompletion 也会兜底置位。模型流仍会跑完（成本已发生），但不会再写响应。

## 4. W2 基线导读（二）：公文抽取 + common 基础设施

### 4.1 抽取链路

```
POST /api/extract {text}
 → ExtractController（@Valid 长度校验；try-catch 模型异常→502）
 → ExtractService.extract
    → ExtractAssistant.chat（@AiService EXPLICIT 绑定 openAiJsonChatModel）
    → 剥 ```json 围栏 → ObjectMapper.readValue
    → 解析失败：不抛错，返回 warnings=["结构化解析失败，请人工核对"]
    → 字段级校验：docType 白名单(通知/请示/报告/函/纪要/其他)、LocalDate.parse 日期
    → 越界字段置 null + 追加 warning
```

关键文件：`config/JsonChatModelConfig.java`（temperature=0.0 + responseFormat("json_object")，即 DeepSeek 的 JSON 模式）、`service/ExtractService.java`、`resources/extract-prompt.md`。

**设计思想：把大模型当"不可靠的外部输入源"**。三层防线：
1. 模型侧：JSON 模式 + temperature 0，尽量输出合法 JSON；
2. 解析侧：剥围栏 + try-catch，乱答不 500；
3. 业务侧：枚举白名单、日期格式校验，越界降级为 warnings 供人工核对。

单测 `ExtractServiceTest` 覆盖 7 个用例（非 JSON、带围栏、文种/日期越界、空文本、超长文本、正常输入），`.\mvnw.cmd test` 离线可跑，不耗模型额度。

**面试问答**

Q：为什么不用 LangChain4j 的 AiService 直接返回 POJO（自动结构化输出）？
A：可以，但自动解析失败会抛异常；这里手动解析是为了**完全掌控降级路径**——失败时返回带 warnings 的部分结果而不是报错。面试可补一句：生产上两者结合，POJO 输出 + 异常时降级。

Q：temperature=0 意味着什么？
A：贪心解码，输出最确定、可复现，适合抽取/分类任务；对话生成才需要 >0 的多样性。

### 4.2 common 三件套

| 文件 | 机制 |
|---|---|
| `TraceIdFilter` | @Order(HIGHEST_PRECEDENCE) 的 OncePerRequestFilter：优先复用请求头 X-Trace-Id（正则 `[A-Za-z0-9-]{1,64}` 校验，防日志注入），否则生成 UUID；写入 request attribute + 响应头 + **MDC**；finally 里 MDC.remove |
| `GlobalExceptionHandler` | @RestControllerAdvice：400（校验/ body 不可读/ IllegalArgument）、401、403、兜底 500；兜底里对 `ErrorResponse` 实例保留 Spring 原始状态码（404/405 不被误改 500）；所有错误体显式 `contentType(APPLICATION_JSON)`（因为流式接口 produces=text/event-stream，内容协商会选错） |
| `ApiResponse` | record {code, message, data, traceId}，全项目统一响应壳 |

日志格式（application.yaml）：`[%X{traceId:-}]` 从 MDC 取值——**同一请求的所有日志自动带 traceId，不用每行手拼**。

**面试问答**

Q：Filter 和 Interceptor 的区别？本项目为什么 traceId 用 Filter、认证用 Interceptor？
A：Filter 是 Servlet 规范层，先于 Spring MVC 执行，能覆盖所有请求（含静态资源、异常路径）；Interceptor 是 Spring MVC 层，能拿到 handler 信息、有 afterCompletion 回调。traceId 要尽早生成、越外层越好→Filter；认证只拦特定 API 路径、需要请求结束清理 ThreadLocal→Interceptor。

Q：MDC 是什么？为什么 finally 里必须 remove？
A：MDC 是 slf4j 的线程级日志上下文（底层 ThreadLocal）。Tomcat 线程池复用线程，不清理会把上一个请求的 traceId 带给下一个请求。**延伸考点：@Async 切线程后 MDC 不会自动传播**——本项目入库线程的日志就没有 traceId，改进要用 TaskDecorator 复制 MDC（见 9.6）。

Q：为什么错误响应要显式设置 contentType？
A：/api/chat/stream 声明了 produces=text/event-stream，异常时若走内容协商可能把 JSON 错误体按 SSE 类型返回，前端解析就乱了。显式 APPLICATION_JSON 覆盖协商结果。

## 5. 认证与权限（auth + kb）

### 5.1 登录与请求认证流程

```
POST /api/auth/login（开放）
 → UserRepository.findByUsername（JdbcTemplate + RowMapper）
 → BCryptPasswordEncoder.matches（只引 spring-security-crypto，不引完整 Security）
 → TokenStore.issue：UUID token → ConcurrentHashMap<String,User>（内存，重启失效）
 → 返回 {token, user:UserView}   ← User.toView() 剥掉 passwordHash

后续请求 Authorization: Bearer <token>
 → WebConfig 注册 AuthInterceptor，只拦 /api/kb/**、/api/rag/**、/api/auth/me|logout
 → preHandle：OPTIONS 预检放行 → extractToken → tokenStore.resolve
    → null 抛 UnauthorizedException(401)；命中 UserContext.set(ThreadLocal)
 → Controller/Service 里 UserContext.currentUser() 随取随用
 → afterCompletion：UserContext.clear()（防线程复用串号）
```

关键文件：`auth/AuthInterceptor.java`、`auth/TokenStore.java`、`auth/UserContext.java`、`auth/User.java`（内部含哈希）vs `auth/UserView.java`（对外）、`auth/AdminSeeder.java`（CommandLineRunner 幂等种子账号）、`config/WebConfig.java`（拦截路径 + CORS）。

### 5.2 权限收口：KbAccessService

**所有权限判断集中在一个类**，其他 Service 只调它的三个方法：

| 方法 | 语义 | 谁在用 |
|---|---|---|
| `canAccess / accessibleKbs / accessibleKbIds` | 可见性：ADMIN 全量；所有者；PUBLIC 所有人；DEPARTMENT 同部门；PRIVATE 仅所有者 | 列表、RAG 缺省检索范围 |
| `requireAccess(user, kbId)` | 读/检索/上传门槛，不过抛 403 | DocumentService、RagChatController |
| `requireManage(user, kbId)` | 改/删知识库：仅所有者或 ADMIN | KnowledgeBaseService.update/delete |

文档删除另有细粒度规则（DocumentService.delete）：ADMIN / 库所有者 / **上传者本人** 三者之一。

**防越权的关键细节**（RagChatController 第 34-35 行）：用户显式传的 kbIds **逐个** requireAccess——不能因为"参数是用户传的"就信任，否则拿到别人 PRIVATE 库的 id 就能检索其内容（水平越权）。

### 5.3 面试问答

Q：ThreadLocal 为什么必须在 afterCompletion 清理？不清理会怎样？
A：Tomcat 线程池复用线程。请求 A 的 User 留在 ThreadLocal，线程被请求 B（未登录路径）复用时，B 里 currentUser() 会拿到 A 的身份——串号事故。afterCompletion 无论成功失败都执行，是清理的正确位置。

Q：内存 token 方案的局限？JWT / Redis 怎么选？
A：内存 Map：重启全掉线、多实例不共享、无过期清理（只增不减，见 9.5）。JWT：无状态、天然多实例，但注销/踢人需要黑名单（又回到有状态）；Redis 集中式：可过期、可注销、可查在线，代价是多一次网络 IO 和 Redis 依赖。学习项目用内存是刻意简化，面试要能说出这条演进路径。

Q：为什么只引 spring-security-crypto 不引完整 Spring Security？
A：只需要 BCrypt 哈希。完整 Security 会默认接管全部路由（表单登录/CSRF/默认 401），与现有开放接口冲突，学习成本高。BCrypt 自带盐、慢哈希抗暴力破解，比 MD5/SHA 适合存密码。

Q：401 和 403 的语义区别？
A：401=没认证（token 缺失/失效），403=认证了但没权限（PRIVATE 库非所有者）。本项目分别对应 UnauthorizedException / ForbiddenException，由 GlobalExceptionHandler 映射。

Q：知识库删除时为什么先删向量再删业务记录？
A：rag_document 有外键级联，业务删除会自动带走文档记录；但向量表不归外键管，必须显式 `embeddingStore.removeAll(kb_id=…)`。先删向量：即使业务删除失败，最多是"库还在但检索不到内容"（可重试删除）；反过来会留下**永远清不掉的孤儿向量**（kb_id 已无对应记录）。注意这两步没有事务保证，是权衡不是完美方案（见 9.7）。

## 6. 文档入库管道（document 包）

### 6.1 链路与状态机

```
POST /api/kb/{kbId}/documents (multipart)
 → DocumentController.upload（UserContext 取用户）
 → DocumentService.upload
    ① kbAccessService.requireAccess        ← 权限第一道
    ② 空文件检查 + 扩展名白名单(pdf/doc/docx/md/txt，toLowerCase)
    ③ file.getBytes() 一次性读入内存
    ④ documentRepository.insert → status=PROCESSING，KeyHolder 拿自增 docId
    ⑤ ingestionService.ingest(...)          ← @Async("ingestionExecutor")，立即返回
    ⑥ 返回 PROCESSING 状态的文档记录，前端轮询 GET documents 等 READY

IngestionService.ingest（ingest- 线程）
 → parser()：switch 扩展名 → PdfBox / POI / Text 解析器
 → 元数据：kb_id / doc_id / file_name（字符串值）
 → DocumentSplitters.recursive(500, 50) 切分
 → 空段守卫：markFailed("文档内容为空或解析失败") + return
 → 每段补 chunk_index → embeddingModel.embedAll（bge-m3，1024 维）
 → embeddingStore.addAll → markReady(docId, chunkCount)
 → 任何异常：markFailed（error_msg 截断 1000 字符，列宽 1024 防二次报错）
```

状态机只有三态：`PROCESSING → READY / FAILED`（RagDocument 里的三个常量）。

### 6.2 关键文件

| 文件 | 看什么 |
|---|---|
| `DocumentService` | 同步部分：权限、校验、落库、触发异步；delete 的三方权限规则 + 先删向量 |
| `IngestionService` | 异步部分：解析器 switch、recursive 切分、元数据注入、失败兜底 |
| `DocumentRepository` | JdbcTemplate + RowMapper + GeneratedKeyHolder（拿自增主键的标准写法） |
| `config/AsyncConfig` | @EnableAsync + 专用线程池（core2/max4/queue100），与 Web 线程隔离 |
| `db/init.sql` | rag_document 外键 `ON DELETE CASCADE`；error_msg VARCHAR(1024) |

### 6.3 核心机制

1. **为什么异步**：解析+向量化可能几十秒，同步做会占死 Tomcat 线程且前端超时。上传接口只做"登记+触发"，毫秒级返回，状态靠轮询。
2. **为什么专用线程池**：默认 @Async 用 SimpleAsyncTaskExecutor（每任务新建线程，无上限）；专用池限流（最多 4 并发入库），防止大批上传打爆 Ollama/内存。
3. **元数据是权限与溯源的载体**：kb_id 用于检索过滤和删除清理，doc_id 用于按文档删向量，file_name+chunk_index 用于回答里的 [n] 引用溯源。**值统一存字符串**（MetadataKeys 注释约定），因为 pgvector 的 metadata JSONB 过滤按字符串比较，Long 和 String 混存会导致过滤失配。
4. **recursive 切分**：按段落→句子→词的层级递归切，500 字符/段、相邻段重叠 50 字符，避免句子被拦腰切断导致语义丢失。
5. **失败可观测**：FAILED 状态带 error_msg，前端能展示失败原因而不是永远转圈。

### 6.4 面试问答

Q：@Async 什么情况下会失效？
A：同类内部自调用（this.ingest() 不走代理）、方法非 public、调用方没被 @EnableAsync 覆盖。本项目 DocumentService 调 IngestionService 是**跨 Bean 调用**，代理生效——这是刻意的设计。

Q：上传接口返回时文档是什么状态？有没有竞态？
A：返回前一刻刚 insert 为 PROCESSING，但异步线程可能已经跑完，findById 再查时可能已是 READY/FAILED。所以返回的 status 只能当"初始快照"，前端必须以轮询为准。这个细节值得主动讲。

Q：为什么用 JdbcTemplate 而不是 JPA/MyBatis？
A：表少、SQL 简单可控，RowMapper 显式映射一目了然；向量表走 langchain4j 专用 Store（有向量协议与索引），两套存储各用各的最自然。面试延伸：复杂业务表会上 MyBatis/JPA。

Q：大文件怎么办？现在 getBytes 全读进内存。
A：已有 multipart 20MB 上限兜底；更大文件应流式解析（InputStream 直传 parser）+ 分段批量 embedAll，避免一次性驻留内存。这是可讲的改进方向。

Q：重复上传同一文件会怎样？
A：当前不去重，会生成新 docId 再入一份向量（检索可能命中重复内容）。改进：按 kb_id+文件哈希做幂等。主动说出局限比被问倒好。

## 7. 混合检索（retrieval 包）

### 7.1 双路检索 + RRF 融合 + 可选重排

```
retrieve(query, keywords, kbIds)
 ├─ 向量路：embed(query) → EmbeddingSearchRequest
 │    .maxResults(20).minScore(0.3)
 │    .filter(metadataKey("kb_id").isIn(kbStrings))   ← 权限过滤下推到向量库
 │    → 按相似度排名 rank=1..n
 ├─ 关键词路：JdbcTemplate 直查 rag_embedding 表
 │    WHERE metadata->>'kb_id' IN (?,?,…) AND (text ILIKE ? OR text ILIKE ?…)
 │    LIMIT 20   ← 全部占位符传参，无 SQL 拼接注入
 └─ 融合：Map<embeddingId, Candidate>
      每路命中都 addRrf(rank)：rrfScore += 1/(60+rank)
      同一 embeddingId 两路都命中 → 分数相加（去重靠 embeddingId）
      → 按 rrfScore 降序取前 20
 → rerank（可选）：ObjectProvider.getIfAvailable()
      有 ScoringModel → scoreAll(segments, query) → 按重排分取前 5
      调用异常 → log.warn 降级用 RRF 排序
      无 Bean → 直接 RRF 排序取前 5
 → List<RetrievalChunk{text, metadata, score}>
```

### 7.2 RRF 为什么是 1/(60+rank) 而不是分数相加

向量路分数是余弦相似度（0~1），关键词路 ILIKE 根本没有分数（只有命中与否）。**量纲不同，直接相加没有意义**。RRF（Reciprocal Rank Fusion）只用**名次**：

- 两路都排第 1 的段：1/61 + 1/61 ≈ 0.0328
- 只在向量路排第 1：1/61 ≈ 0.0164
- 只在向量路排第 10：1/70 ≈ 0.0143

双路共识 > 单路高名次；k=60 是经验常数，作用是压平头部差距（第 1 名和第 2 名分差很小），让"多路都认可"的段更容易胜出。

### 7.3 关键文件与配置

| 文件/配置 | 值 | 说明 |
|---|---|---|
| `HybridRetrievalService` | RRF_K=60 | 双路+融合+重排全部在这一个类 |
| `MetadataKeys` | 四个常量 | 入库/检索/删除三方共用，防手滑写错键名 |
| `RetrievalChunk` | record | 检索结果统一载体 |
| `rag.retrieval.*` | vector-top-k=20, keyword-top-k=20, final-top-k=5, min-score=0.3 | 召回宽、出口窄 |
| `ScoringModelConfig` | @ConditionalOnProperty + 空 key 返回 null | SiliconFlow /rerank 与 Jina 格式兼容，复用 JinaScoringModel |

**降级双保险**（面试好素材）：`@ConditionalOnProperty(name="rag.rerank.api-key")` 对"属性存在但为空串"仍然匹配（yaml 里默认值就是空串），所以 Bean 方法里还要判空返回 null；消费方用 `ObjectProvider<ScoringModel>.getIfAvailable()` 拿不到就走 RRF 排序。**任何一层失效都不会让链路 500**。

### 7.4 面试问答

Q：为什么要关键词路？向量检索不够吗？
A：向量擅长语义相似（"离职证明"↔"解除劳动关系文件"），但对**精确术语/编号/生僻词**（如"深人社规〔2023〕5 号"）embedding 区分度差；关键词 ILIKE 精确兜底。两路互补，RRF 融合。

Q：kb_id 过滤为什么下推到向量库，而不是查回来再内存过滤？
A：先过滤再取 topK，保证返回的 20 条**全部**在权限范围内；若查回再过滤，可能 20 条里 19 条是别人库的，过滤后只剩 1 条，召回质量崩了。这就是"多租户隔离下推"。

Q：rerank 和 embedding 检索的区别？
A：embedding 是 bi-encoder，query 和文档**各自独立**编码，快但粗；rerank 是 cross-encoder，query+文档**拼在一起**过模型，交互充分、精度高但慢，所以只对融合后的 20 条精排取 5 条。"召回宽、精排窄"是标准漏斗。

Q：ILIKE '%kw%' 的性能问题？
A：前置通配符走不了 B-tree 索引，全表扫。数据量大时应换 PostgreSQL 全文检索（tsvector+GIN，中文需 zhparser/jieba 分词）或 pg_trgm GIN 索引。当前学习规模够用，但要能说出演进路径。

Q：minScore=0.3 拦的是什么？
A：向量路的低相关噪声（余弦相似度阈值）。注意关键词路没有分数门槛，靠 RRF 名次自然压制。

## 8. langgraph4j 状态图问答（graph 包）

### 8.1 图结构

```
START → retrieve → evaluate ─┬─ sufficient=true ────────→ generate → END
                             ├─ false 且 retryCount<2 ──→ rewrite ─→ retrieve（环）
                             └─ false 且 retryCount≥2 ──→ generate（明示资料不足）
```

四个节点都是 RagWorkflow 的私有方法，`node_async(this::retrieve)` 包成异步动作；**节点只返回增量 Map**（如 `Map.of(CONTEXT, …, CHUNKS, …)`），由框架按 SCHEMA 合并进 State。

### 8.2 关键文件

| 文件 | 看什么 |
|---|---|
| `RagState` | 10 个字段的 SCHEMA：`Channels.base(() -> 默认值)` 声明覆盖式合并；每个字段一个类型安全读取器 `value(KEY).orElse(默认)` |
| `RagWorkflow` 构造器 | addNode → addEdge → addConditionalEdges(路由函数, 映射表) → compile()，图在 Bean 构造时编译一次 |
| `RagWorkflow.chat` | `invoke(Map, RunnableConfig.builder().build()).orElseThrow()`——1.9.7 正确签名 |
| `retrieve/evaluate/rewrite/generate` | 四个节点的业务逻辑 |
| `Workflow.java` + `State.java` | **独立教学 demo**（main 方法、模拟检索、手动读 .env），与生产链路无关 |
| `Node.java` | 全文注释掉的遗迹，可忽略 |

### 8.3 核心机制

1. **evaluate/rewrite 用 JSON 模型**：`openAiJsonChatModel`（temperature 0 + json_object）输出 `{"sufficient":bool}` / `{"query":…, "keywords":[…]}`；解析失败**不抛错**——evaluate 按"不足"处理，rewrite 用原问题重试。generate 用普通 `openAiChatModel`（两个 Bean 靠 @Qualifier 区分）。
2. **重试计数在 rewrite 里 +1**：首次检索不计数，最多额外重试 2 次（rag.retry.max=2）。条件边映射表覆盖路由函数全部三个返回值 ok/retry/fallback——漏一个编译期就报 GraphStateException。
3. **两道死循环防线**：业务 retryCount 保证**优雅降级**（走 fallback 正常生成"资料不足"回答）；框架 RunnableConfig.recursionLimit（默认 25 步）保证路由写错时**强制熔断抛异常**。层级不同，缺一不可。
4. **引用溯源**：retrieve 把每段编成 `[n] (来源: xxx.md)` 拼进 context；generate 的提示词要求句末标 [n]；sources 原样返回 chunks（index/text/file_name/score），前端可渲染引用卡片。
5. **1.9.7 API 契约**（历史踩坑，面试可当"版本迁移"故事）：
   - `Channels.base()` 无参重载已移除 → 必须 `Channels.base(() -> 默认值)`
   - `invoke(Map)` 单参已 @Deprecated(forRemoval) → `invoke(Map, RunnableConfig.builder().build())`
   - 返回 `Optional<State>`，只 orElseThrow() 一次
   - 节点接口是 `org.bsc.langgraph4j.action.NodeAction`（函数式），**不是** annotation 包里的同名注解
6. **教学 demo Workflow.java 的价值**：用模拟检索（第一次故意给不足资料）隔离"图逻辑"与"LLM 集成"两个变量，先跑通环和条件边再接真模型；它的 env() 方法手动加载 .env，因为**普通 main 没有 Spring 容器，@Value 占位符不会被解析**。

### 8.4 面试问答

Q：为什么用状态图而不是 if-else 顺序调用？
A：三个理由：① 环（评估-改写-重试）用图表达是显式的边，if-else 里是藏起来的循环，可维护性差；② State 集中管理中间产物，节点间不传长参数列表；③ 框架自带 recursionLimit、可挂 CheckpointSaver 做断点续跑/多轮记忆（threadId），if-else 全要手写。

Q：State 的 Channel 是什么？
A：定义每个字段的**合并策略**。本项目全部用 base（覆盖式，新值替换旧值）；LangGraph 还有 appender 通道（列表追加，适合消息历史）。节点返回增量 Map，框架按 SCHEMA 逐字段合并——这就是"状态图"和"普通函数调用"的本质区别。

Q：图为什么在构造器里 compile？
A：图结构是静态的，编译一次复用（线程安全），每次请求只 invoke。避免每请求建图的开销；代价是启动时若图有错（边缺失/映射不全）Bean 创建直接失败——**错误前置到启动期**，反而是好事。

Q：evaluate 判断错了怎么办（资料明明够却判不足）？
A：最多多重试 2 次后走 fallback，回答里明示资料不足，不会编造——错误代价是延迟而非错误答案。反过来"资料不够却判够"由 generate 提示词第 2 条兜底。LLM 判断不可靠时，用流程设计限制其破坏半径。

Q：这套和 RAGFlow/Dify 的自适应检索是什么关系？
A：思想同源（Self-RAG/CRAG 的评估-改写环），本项目用 langgraph4j 手写实现，能讲清每个节点；框架产品是黑盒。面试讲手写实现更加分。

## 10. 通读中发现的问题与思考点（不改代码，留你判断）

以下是逐文件通读时发现的真实问题/可改进点，按"建议优先级"排序。每一条都是面试好素材（"我知道自己项目的局限"）：

1. **DocumentService.upload 的 NPE 风险**：`file.getOriginalFilename()` 可能为 null，先赋给 filename 再检查 isEmpty，随后 `filename.substring(...)` 会 NPE；文件名无 "." 时 lastIndexOf 返回 -1，ext 会变成整个文件名。应先判空再解析扩展名。
2. **TokenStore 无过期/淘汰**：ConcurrentHashMap 只增不减（logout 才 remove），长期运行内存增长；且重启全员掉线。演进：定时清理 + TTL，或换 Redis/JWT（见 5.3）。
3. **@Async 线程丢 traceId**：MDC 是 ThreadLocal，ingest- 线程的日志没有 traceId，入库失败时无法从上传请求的 traceId 串到失败日志。改进：TaskDecorator 复制 MDC，或 ingest 参数显式传 traceId。
4. **accessibleKbs 全表加载后内存过滤**：KbRepository.findAll() 拉全部再 stream filter。库多了应把可见性规则下推 SQL（WHERE owner_id=? OR visibility='PUBLIC' OR …）。
5. **知识库/文档删除无事务**：先删向量后删业务行，中间失败会留下"空壳库"（可重试，危害小）；但两步不在一个事务里，严格一致性需要补偿任务或先标记后清理。能讲清"为什么选这个顺序"就够了（见 5.3）。
6. **ExtractController 的成功 code=0**，其他接口都是 200；且它自己 try-catch 转 502，与 GlobalExceptionHandler 职责重叠。统一风格是可讲的重构点。
7. **融合后 limit 用的是 vectorTopK(20) 而非 finalTopK**：语义上碰巧合理（召回宽、rerank 后取 5），但变量名与意图不匹配，读代码时容易困惑——可考虑引入专门的 rerankTopN 配置。
8. **关键词路 ILIKE 无排序**：LIMIT 20 取的是数据库任意顺序，"rank"其实是伪名次；严格做法是按命中关键词数排序。当前规模影响小。
9. **代码卫生**：RagState 有无用的 `@Configuration` import；EmbeddingController 是空壳；MemoryConfig 有无用 import；graph/Node.java 全注释。不影响运行，但提交前值得清理。
10. **上传即返回的竞态**：见 6.4 Q2，前端必须以轮询为准，不能信任上传响应里的 status。

### 11.4 STAR 叙事模板（自适应检索为例）

- **S**：知识库问答中，用户问法和文档措辞常常对不上，单次向量检索命中率低，直接生成会编造。
- **T**：在不牺牲响应时间的前提下提高命中率，且资料不足时必须明示而非编造。
- **A**：用 langgraph4j 把检索编排成状态图：双路召回+RRF 融合提高单次命中；evaluate 节点用 JSON 模式 LLM 判断资料充分性；不足则 rewrite 改写查询+提关键词再检，最多 2 次；业务重试计数保证优雅降级，框架 recursionLimit 做熔断兜底；rerank 无 key/调用失败自动降级不中断链路。
- **R**：问库内问题一轮直达（retryCount=0）；问库外问题两轮后明示"资料不足"，不编造；回答带 [n] 引用可溯源。（补上你自己实测的延迟/命中对比数据更有说服力）
